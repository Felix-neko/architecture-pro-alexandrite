# Задание 1. Планирование: анализ, идентификация проблем и поиск решений

## Проблемные места

### Текущие проблемы

Проблемы, которые уже приносят убытки:

* Потеря данных о заказах.  
* Медленно открывается главная страница MES.  
* Медленный расчёт стоимости в MES.  
* Очень большие задержки релизов.  
* Некоторые баги не удаётся локализовать из\-крайне слабых возможностей по диагностике (т.к. микросервисную архитектуру внедрили, а средства диагностики нет).

### Потенциальные проблемы

* Команда слишком мала даже для текущих задач.  
* Горизонтальное масштабирование сервисов не применяется  
* Централизованный сбор логов не применяется  
* Средства распределённой трассировки тоже не применяются  
* Нет централизованного мониторинга  
* Резервное копирование: статус неизвестен  
* Нагрузочного тестирования системы нет  
* E2E-тестирование нужно автоматизировать  
* CRM и интернет-магазин синхронизируются только БД  
* Судя по диаграмме контейнеров, интернет-магазин и CRM синхронизируют новые заказы только через БД (видимо, опрашивая БД раз в какое-то время). Это даёт и дополнительные задержки (неудобство для пользователя), и дополнительную нагрузку на БД.

## Мероприятия для исправления ситуации

Важно: для разработчиков поддержа логирования важнее всего, затем поддержка трассировки и мониторинга. Пока они не заработают, попытки диагностики сбоев рекомендую отложить и сосредоточиться на этом вещах. Любую разработку нового функционала – тоже рекомендую отложить до того, как будует поддержаны логирование, трассировка и мониторинг.

Для девопсов – сначала переезд на Kubernetes, потом развёртывание средств логирования, трассировки и мониторинга.

Меры по исправлению ситуации, в порядке убывания приоритета, ниже.

### Найм новых сотрудников

#### DevOps-инженеры

 (+2-3 человека), т.к. предстоит переход на Kubernetes и нужно будет развёртывать много сложных инфраструктурных сервисов, а потом их поддерживать и развивать.

- По опыту работы: все должны работать с Kubernetes. Желательно, чтобы хотя бы у одного из них уже был опыт работы с ELK.

#### QA-инженеры

 (+1-2) с опытом разработки автотестов, чтобы заняться автотестами E2E-сценариев, а руками тестировать только то, что правда трудно автоматизировать.

#### Разработчики

Хотя бы по одному разработчику на C\# и Java (т.к. нынешняя команда не успевает обработать даже текущий бэклог, не говоря уже о поэтапном внедрении трассировки и мониторинга для сервисов).

### Переход на Kubernetes

Для начала – можно воспользоваться Managed Kubernetes от Yandex Cloud, потом можно поднять свой кластер, чтобы меньше проблем с хранением персоналки).

Переходить на Kubernes в любом случае придётся, так как:

- нам нужны возможности по горизонтальному масштабированию сервисов, доступные в Kubernetes;  
- нам нужна возможность быстро и безболезненно разворачивать и настраивать различные сервисы, особенно с помощью механизма helm chart;  
- БД, находящиеся на отдельном провайдере, явно вносят дополнительную задержку;  
- исполнение всех сервисов внутри одного Kubernetes-кластера решает и много потенциальных проблем с безопасностью

### Внедрить сбор логов в ELK

* Установить ELK и включить туда сбор логов со всех сервисов (всё, что они пишут в stdout и stderr, срок хранения не менее 60 суток).  
* Провести для разработчиков мастер-класс по правильному формированию логов (уровни логирования, предоставить стандартизированные JSON-форматы сообщений, научить вставлять специальные теги для более удобного поиска в логах).  
* Провести для разработчиков мастер-класс, как правильно искать в логах ElasticSearch через Kibana (это не самая тривиальная задача).

### Внедрить сквозную трассировку через OpenTelemetry \+ Jaeger

* Развернуть Jaeger.  
* Провести среди разработчиков мастер-класс, как правильно читать телеметрю в Jaeger Web UI и находить там непрохождение запросов. Нужно разобрать несколько примеров: синхронных запросов между 2-3 сервисами и асинхронной передачи данных между сервисами через очередь.  
* Доработать сами сервисы, чтобы они отправляли телеметрию в Jaeger.

### Внедрить мониторинг (Prometheus \+ Grafana)

* Readiness Probe для всех сервисов, включая БД и брокеры сообщений  
* Мониторинг ресурсов, потребляемых каждым контейнером (CPU, RAM, место на дисках, нагрузка на диски и сеть).  
* Нагрузка на бэкэнд: RPS, CU  
* Длительность обработки HTTP-запросов  
* Длительность обработки запросов к БД  
* Количество необработанных данных в очередях  
* Количество ошибок при обработке HTTP-запросов.

### Наладить резервное копирование

Если его ещё нет – срочно внедряем.

### Поддержать горизонтальное масштабирование при расчёте стоимости

Расчёт стоимости изделия должен быть вынесен в отдельный микросервис, который должен запускаться в несколько реплик паралелльно.

### Предоставить разработчикам удобные средства отладки в Kubernetes-среде

Чтобы разработчики могли оперативно чинить баги, которые возникают именно внутри kubernetes, у них должна быть возможность вести отладку с breakpoint’ами непосредственно внутри  dev- и release-среды Kubernetes.  
Это должна быть или отладка с помощью удалённого интерпретатора с подключением по SSH, или возможность запустить IDE непосредственно внутри Kubernetes (например, с использованием VNC).

### Поддержать кэширование данных для MES

Особенно в части загрузки главной страницы.

# Целевая архитектура через полгода

* Сервисы перенесены на Kubernetes-кластер, БД тоже перенесены на Kubernetes.  
* Налажен централизованный сбор логов, в т.ч. сырых логов (всё, что сервисы пишут в stdout и stderr, попадает в отдельные индексы ELK).  
* Во время основных операций в сервисах (включая обращения к очередям и БД) отправляется телеметрия в Jaeger..  
* Сервисы отдают метрики в Prometheus.  
* Нагруженные сервисы, начиная с MES, поддерживают горизонтальное масштабирование через StatefulSet.  
* Доступ к сервисам извне осуществляется через API Gateway с балансировкой нагрузки, используются Sticky Sessions.  
* Для веб\-сервиса MES используется кэширование главной страницы.  
* Интернет-магазин и CRM также обмениваются данными не через БД, а через очередь.

## Три главных пункта

* Запуск найма. Ибо команда явно перегружена даже текущими задачами.  
* Kubernetes. Иначе каждый дальнейший шаг по развёртыванию любого сервиса будет отнимать очень много сил, да и сбор логов превратится в ад.  
* Логи. Без мониторинга и OpenTelemetry выжить ещё можно, без полноценных логов – нельзя (даже если есть мониторинг и OpenTelemetry, разработчики потом всё равно идут искать в логах, просто более прицельно).
