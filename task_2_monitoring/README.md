# Задание 2. Мониторинг

# Мотивация

“Яндекс-Метрика” может показывать поведение пользователей и состояние воронки продаж. Она и так работает прекрасно, судя по росту заказов.

Но: несмотря на отличный маркетинг, у нас много технических сбоев и критических задержек при обработке запросов пользователей, что резко ухудшает пользовательский опыт и уже отвернуло от нас нескольких крупных бизнес-заказчиков.

При этом:

- некоторые сервисы (как минимум, MES API) явно перегружены;  
- некоторые сбои могут возникать, когда перегружен либо сам сервис, либо сервисы, к которым он обращается.

Нам нужны метрики для отслеживания внутреннего состояния наших подсистем, чтобы отследить источники сбоев и задержек

# Подход к метрикам

## RED

Для всех сервисов, чьё API торчит наружу:

* MES API (приоритетно)  
* Shop API  
* CRM API

## USE

Для очередей сообщений, S3-хранилища и БД.

## 4 золотых сигнала

- MES API  
- БД (важно проверить, насколько велика сетевая задержка из\-за того, что БД и сервисы расположены на разных кластерах).

# Подробный список метрик

Для всех сервисов:

- liveness probe  
- CPU usage  
- RAM usage  
- Disk usage  
- Disk I/IO  
- Network I/O

Для БД:

- RPS;  
- CCU;  
- время выполнения SQL-запросов (через pg\_stat\_statements \+ pg\_exporter, лейблы по умолчанию);  
- количество ошибок.

Для очереди сообщений:

- RPS  
- CCU;  
- количества необработанных сообщений в топиках;  
- размеры Dead Letter Exchange (т.е. отвергнутых сообщений или сообщений с исчерпанным TTL).

Для S3-хранилища:

- RPS  
- CCU  
- размеры отдаваемых файлов (при чтении);  
- размеры записываемых файлов (при записи);  
- количество ошибок при чтении;  
- количество ошибок при записи;

Для веб\-сервисов, предоставляющих REST API  
 (MES API, Shop API, CRM API):

- RPS  
- CCU  
- Время обработки запроса (лейбл по HTTP Path)  
- Количество ошибок (лейбл по HTTP Path)

Если есть методы, вызываемые по расписанию (например, если CRM API проверяет в БД, не появились ли там новые заказы от Shop API):

- время работы метода (лейбл по названию метода)  
- количество ошибок метода (лейбл по названию метода)

Если есть методы, вызываемые при считывании данных из очереди (с лейблом по названию метода в Java/C\#):

- общее время работы метода;  
- время чтения данных из очереди;  
- количество ошибок при чтении данных из очереди;  
- количество событий из очереди, обработка которых завершилась ошибкой (особенно для MES API).

# План действий

## Для девопсов

Хинт: работы по метрикам – только по завершении работ по логам.

Основные задачи:  
\- развернуть Prometheus \+ Grafana (helm chart kube-prometheus и grafana от bitnami вполне годятся)  
\- включить сбор метрик для инфраструктурных сервисов (БД, S3-хранилище, брокер сообщений)  
\- создать и проверить дэшборды для инфраструктурных third-party-сервисов  
\- создать и проверить дэшборды для собственных сервисов компании (когда разработчики поддержат сбор метрик в этих сервисах).

## Для разработчиков

Учитывая крайне малочисленную команду, общий порядок такой: логи \>\> метрики \>\> трассировка \>\> поиск багов с повторением клиентского пути (но уже с лучшими возможностями по отладке).

Сответственно, поддержка метрик в собственных сервисах – только после того, как будет поддержан полноценный сбор логов в них.
